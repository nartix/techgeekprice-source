# Spring OpenAPI contracts

The versioned `spring.openapi.json` is the **unmodified public runtime export** from Spring at the revision/hash in `provenance.json`. It is build input, not a frontend-authored replacement schema. `src/generated/spring.ts` is generated, never hand-edited. Normal generation and CI/typecheck need no backend, network or credentials.

From the repository root:

```sh
pnpm contracts:generate
pnpm contracts:check
pnpm --filter @tgp/contracts test
pnpm --filter @tgp/contracts typecheck
```

`contracts:check` regenerates in memory and compares bytes, including the snapshot SHA-256. It fails without overwriting stale output. `typecheck` runs this check, so existing root validation also enforces freshness. The generator rejects every non-fragment `$ref` before invoking the library; there are no remote schema dependencies. Pinned generator version: 7.13.0. Generated TypeScript provides static checks; it does not validate live responses.

## Export and provenance

The snapshot was exported on 2026-11-16 from the backend source revision recorded
in `provenance.json`. That revision predates the public snapshot's fresh history.
The file contains public API schema annotations, not authenticated response data.
To update, start the sibling backend with your own configuration, then export:

```sh
curl --fail --silent --show-error http://127.0.0.1:8080/v3/api-docs -o /tmp/spring.openapi.json
```

Replace the versioned file with the reviewed raw export, update `provenance.json` (backend revision, export date, SHA-256), regenerate, and rerun tests/typechecks and API integration regressions. Shutdown only resources started for export. Never include cookies, passwords, access tokens, private configuration, or authenticated response examples. Public annotation examples in the schema are source documentation, not live account records.

The app currently registers users and the catalogue category system; the typed category template supports other safe system keys. Query arrays use repeated parameters; numbers/booleans are decoded only without loss, then serialized using URLSearchParams. User-facing Refine page numbers stay one-based, translated to Spring page zero; default size 20/max100 and page/data/sort/links mapping are unchanged. All matrix operations route through literal generated signatures when inputs fit the documented schema, except the manual exceptions below. Real Refine/auth adapter tests assert the generated schema paths as well as the wire requests. Unsupported/malformed dynamic inputs retain existing server validation through the legacy path instead of silently dropping fields. The direct `createAdminOpenApiClient` statically checks endpoints/params/bodies; the generic Refine response API remains a caller-owned compatibility boundary.

## Schema gaps and manual exceptions

- **Success status/body omissions**: `iam/api/AdminUserController.java` and `category/api/AdminCategoryController.java` return 201 for creates and 204 for deletes; category move/activate/deactivate also return 204. The snapshot lists 200 instead. The generated transport preserves the actual 201/204 status and the existing empty-result adapter rather than fabricating schema status entries. For no-content 204/205 responses, the response wrapper uses a null body even when Chromium exposes an empty network stream; otherwise constructing the wrapper throws after a successful deletion. Regression coverage exercises the exposed-stream response and preserves status/request-ID headers. Category reorder returns a detail DTO from source, but its 200 schema has no content declaration: its response shape remains the explicitly untyped/generic compatibility result even though its path, parameters and request body use generated types. User CRUD/status failure responses are also incompletely documented; `iam/api/IamApiExceptionHandler.java` maps not-found/duplicate errors to 404/409, while platform validation/security handlers own 400/401/403 and unexpected failures. All statuses continue through the shared runtime error translator; a missing documented error response is not treated as an impossible HTTP status.

Source paths below are in `nartix/spring-api-source/src/main/java/com/ferozfaiz/uniapi/` at the recorded revision.

- **POST `/auth/login`, `/auth/logout`**: absent from the schema because `platform/security/session/AdminSessionSecurityConfiguration.java` installs security filters. Login uses URL-encoded username/password; success/failure/status and logout behavior are implemented in `SessionJsonAuthenticationHandlers.java` and `SessionSecurityExceptionHandlers.java` in that package. Preserve manual requests and existing response DTOs; no invented OpenAPI paths.
- **GET `/auth/csrf`**: `iam/api/auth/AdminSessionAuthController.java` receives a server-injected `CsrfToken`. Schema incorrectly declares required client query `csrfToken`. Keep the request manual and derive its response fields from `CsrfTokenResponse`. The server sets scoped cookies; writes always acquire a fresh token and include its returned header, even for login/logout. The schema's bearer security metadata is not a reason to add bearer auth: admin sessions use the ordered session security filter and HttpOnly cookies.
- **Required/nullability metadata**: many Java records are emitted with every field optional and nullable references emitted as non-null. Compatibility DTOs derive named properties from generated components with required-field/nullable/optional refinements matching existing exports; they do not alter the raw schema. Evidence: the `category/api/dto/` records, `iam/api/dto/AdminUserResponse.java`, and the pagination/error records listed under Verified DTO source locations below. Root parents/ranks, parent-option disabled reasons/cursor and capability limits can be null. Existing optionality is retained for compatibility.
- **Category mutation nulls**: create/update/move/reorder root/placement fields can be explicitly null in backend DTOs, but the schema rejects null. These calls use the legacy transport only when their runtime shape does not fit generated types. Non-null schema-compatible calls use generated bodies. No null-stripping or broad cast changes their meaning.
- **Category merge PATCH**: docs specify only an unconstrained object for JSON/merge-patch. Keep dynamic PATCH manual to preserve merge-patch content and validation; no fabricated field-level type safety.
- **Capabilities**: source `category/api/dto/AdminCategoryCapabilityResponse.java` uses string lists/properties with known frontend vocabulary. Keep public enum/vocabulary refinements and the application's existing runtime capability validation. Generated raw properties remain strings. `AdminCategoryMoveDto` retains its prior narrow newParentId-only export; the generated request additionally documents placement fields.
- **Generic pages/access-option records**: `/users`, `/roles`, `/permissions` success responses use generic `PageResponse` with unknown data items; role/permission option components are absent. Keep typed item refinements from `iam/api/dto/{AdminUserResponse,AdminRoleOptionResponse,AdminPermissionOptionResponse}.java`. Generic page DTO supplies data/page/sort/links compatibility; base metadata/links/sort fields derive from generated components. Lowercase sort directions remain an accepted compatibility vocabulary alongside generated uppercase directions.
- **Identifiers and identity scope**: user path parameters and `iam/api/auth/SessionIdentityResponse.java` identity IDs are numeric, while existing public identity DTO expects a string and open lowercase scope. Preserve that legacy DTO boundary; do not fabricate a schema change or normalize runtime values during this migration. `AdminUserResponse` IDs are already strings in both source and schema. Unsafe/leading-zero numeric path values retain legacy transport without rounding. The application's existing identity mapping/permission logic stays responsible for its view models.
- **Open-ended Refine extensions**: unknown paths/methods/query keys, noncanonical numeric/boolean representations, nullable or incompatible bodies, non-JSON bodies and unusual fetch options retain manual generic handling. This preserves extension/server-validation behavior, not a claim of static checks on arbitrary strings. Documented schemas are used for the listed compatible operations. `AdminProductDto` is an unconsumed admin placeholder contract with no registered admin product endpoints and remains manual.

Existing input/runtime validation, cookie/proxy behavior, cancellation/stale-result suppression, safe error translation and outage/session recovery are retained. Empty success bodies still map to null at the compatibility boundary; malformed successful JSON raises JsonParseError; error status remains authoritative even for unreadable/malformed/non-JSON bodies. There are no automatic mutation retries or CSRF-cache optimizations.
